# 项目现状评估与改进路线图

> 评估基线：2026-09-01
>
> 评估范围：当前工作树、架构/数据模型/扩展设计文档、已有测试与工程脚本
>
> 文档性质：面向后续开发、排期和验收的工程评估，不是发布承诺

> 当前复核：2026-09-12。阶段四公共能力的代码已在后续提交中实现并继续收口；本文表格保留 2026-09-01 的历史基线，当前未完成项以阶段四实施记录及本次验证结果为准。主题插件与运行产物仍不计入完成度。

## 1. 总体结论

项目已经具备一个边界清晰的个人博客核心产品：单站点、单 Owner、文章/页面、Markdown、不可变修订、发布/定时发布、主题、可选插件、备份恢复和 CLI 运维闭环都已经形成。整体架构不需要推倒重来，也不建议为了“看起来更现代”而引入 SPA、Redis、独立搜索服务或多用户模型。

当前最值得投入的方向是生产强化和契约闭合：把已经存在的设计约束落实到所有调用路径，并让失败、重启、代理部署、大数据量和主题升级等场景都可观察、可恢复、可验收。

简要判断如下：

| 领域 | 当前判断 | 主要缺口 |
| --- | --- | --- |
| 核心内容模型 | 稳定 | 编辑效率、批量操作、修订对比仍可增强 |
| 发布与一致性 | 基础闭环已形成 | 定时发布、事件派发、外部副作用尚未完全统一 |
| 安全基线 | 较完整 | 反向代理下的客户端识别、公开写入防滥用、外发网络策略需加强 |
| 主题与插件 | 已有安全边界 | 设置、版本契约、安装验证、路由命名空间和运行时一致性未完全闭合 |
| 性能与规模 | 适合小到中等规模 | 列表带正文、N+1、无界加载和搜索同步路径会限制增长 |
| 运维与恢复 | CLI 能力较丰富 | 加密、异地备份、任务可观测性和 Web 运维入口不足 |
| 公共发现/API | 基础能力齐全 | SEO 元数据、API 分页/缓存/安全细节仍有提升空间 |

## 2. 已经做得好的部分

以下能力应继续保持，不应在后续改造中被稀释：

- 单站点/单 Owner 的产品边界明确，避免了不必要的 RBAC、多租户和读者账户复杂度。
- Markdown 正文、不可变 `content_revisions` 和稳定 permalink 是正确的权威数据设计；缓存、搜索索引和媒体变体均可重建。
- 已有 WAL、外键、忙等待、单写连接、受限读池和事务边界等 SQLite 约束，符合低资源自托管场景。
- 主题采用受限 `html/template`，插件通过窄接口接入，默认关闭插件，安全方向正确。
- 已有测试、竞态检测、vet、性能门禁、Compose 配置检查、SBOM/license 检查和浏览器回归脚本，工程化基础较好。
- 设计文档已经明确了“不引入多用户、不把缓存当权威、不在事务中做网络/重处理”等重要不变量。

## 3. 优先级定义

- **P0：生产风险或数据/安全/可靠性问题。** 应先于新产品功能处理。
- **P1：架构契约、运维能力或规模上限问题。** 不一定立即阻断上线，但会增加后续维护成本。
- **P2：产品体验、增长和高级能力。** 在 P0/P1 收敛后按用户价值排期。

## 5. 关键问题详解

### 5.1 反向代理与公开写入安全

当前 Compose 部署由 Caddy 转发到应用，但以下路径仍直接或间接使用连接地址：

- `internal/identity/http.go` 的客户端地址用于登录保护；
- `internal/comments/http.go` 的评论限流使用 `RemoteAddr`；
- `internal/analytics/service.go` 及展示层使用连接地址推断访客；
- 评论、订阅等公开写入缺少统一的反重放和业务幂等层。

建议先建立一个平台级的“客户端身份与公开写入”边界，避免各模块各自解析请求头。配置至少应包括可信代理网段、是否允许直连、匿名写入的窗口/容量和幂等键有效期。解析顺序应是：可信代理链中的第一个非可信地址，其次才是直接连接地址；未配置可信代理时，所有转发头均视为不可信。

同一边界还应统一处理 Origin/CSRF 已有策略之外的公开写入问题：请求指纹、幂等键、重复评论、评论内容速率、订阅邮箱速率和失败审计。邮箱退订应使用签名、过期时间和用途绑定的 token，而不是仅凭邮箱地址执行。

### 5.2 发布事件、outbox 与外部副作用

当前发布模型已经具备事件和任务的基础，但契约还没有覆盖所有发布来源：手动发布、定时发布、取消发布、删除、主题激活等路径需要逐一核对。特别是定时发布应与手动发布产生相同语义的 `ContentPublished.v1` 事件，而不是只修改数据库状态。

建议采用以下顺序：

1. 在同一个短 SQLite 事务中写入业务状态和 outbox 记录。
2. 提交后由有界 worker 扫描 outbox，创建或执行 durable task。
3. 每个事件和任务带版本、幂等键、尝试次数、租约过期时间和下一次执行时间。
4. 外部 Webhook、通知和搜索同步只在事务外执行；失败时重试，不回滚已成功的内容发布。
5. 管理台提供待处理、重试中、失败和已完成的最小可见性，并支持安全重试。

这样可以把“业务数据已提交”和“外部系统已收到”明确分开，既避免事务过长，也避免进程退出造成不可解释的半完成状态。

### 5.3 媒体封面为何属于 P0

数据库迁移中已经有内容封面字段，展示模型也准备了 `Cover`，但若中间的 publishing model、查询和 `articleData` 没有贯通，用户会得到一种危险的不一致：后台看似保存成功，公开文章列表或主题页面却没有封面，或回滚/导入后丢失引用。

实现时应以“引用关系”作为核心，而不是只增加一个 URL 字段：

- 修订或编辑快照保存媒体引用，发布时生成公开不可变视图；
- 删除媒体前检查内容、正文和变体引用；
- 公开输出只暴露安全的媒体 URL 和有限的变体信息；
- 导入、归档、API 和主题渲染使用同一套封面语义；
- 缺失变体或损坏图片时回退到原图/无图，不阻断文章正文。

### 5.4 主题和插件契约

主题系统的安全方向是正确的，但“能安装”与“能稳定运行”之间还需要一层契约验证。建议将主题安装流程固定为：读取 manifest → 检查路径/大小/文件数 → 校验模板和静态资源 → 校验 API 兼容性 → 使用固定 fixture 渲染 → 写入安装记录 → 原子激活 → 失败回退。

fixture 至少覆盖空列表、中文和英文混排、超长标题、无封面/有封面、404、预览、窄屏语义和管理台共享的主题偏好。主题设置需要有 schema、默认值、类型校验、敏感字段标记和渲染时的只读视图；模板不得直接读取环境变量、数据库或插件私有配置。

插件方面，应把路由注册限制为插件命名空间下的相对路径，并在注册期拒绝宿主路径、重复路径和跨插件覆盖。设置校验、事件版本、任务幂等和禁用后的数据保留都应有自动化测试。当前工作树中存在主题相关未提交改动，本评估将其视为开发中的能力，不等同于已经完成安装/激活/浏览器回归验收。

### 5.5 数据量增长后的性能上限

目前最需要避免的是“列表操作顺手带出完整正文”。管理台 dashboard、内容列表和公开内容列表应使用轻量投影；正文只在详情、编辑和确实需要渲染的路径加载。分类/标签富集应改为批量查询，避免每篇文章重复访问数据库。

建议建立四个可量化门槛：

- 列表接口不读取 `body_markdown`；
- 列表响应的项目数、正文大小、媒体变体数和并发数均有上限；
- 公开页面的 taxonomy 查询次数不随文章数线性增长；
- 搜索索引同步、页面缓存重建和媒体处理均通过有界后台任务执行。

缓存未命中时可增加按 key 的请求合并，避免多个并发请求重复渲染同一个页面；但仍要保留现有 `render_epoch` 失效语义，不能让请求合并替代正确的缓存失效。

### 5.6 备份、恢复和运维闭环

备份包含认证相关敏感数据，当前未加密记录不应被误解为安全备份。建议提供可选的 age 文件加密或外部 KMS 适配，但密钥管理必须在应用外或通过受限 secret 注入完成。无论是否启用加密，都应保留：备份 manifest、大小/校验和、创建时间、应用版本、迁移版本和恢复前校验结果。

运维视图不必一开始做成复杂监控平台，先补充以下信息即可：数据库/迁移状态、最近一次成功备份和验证、备份年龄、失败任务、下一次重试、数据锁、媒体存储使用量和最近恢复结果。恢复演练应在隔离目录或临时实例中进行，并验证健康检查、首页、登录和一篇带媒体的文章。

## 6. 推荐实施顺序

### 阶段一：生产安全与一致性

- 完成可信代理客户端身份解析，并替换登录、评论和 analytics 的散落实现。
- 为评论和订阅增加幂等、重复指纹、退订签名和基础反滥用策略。
- 统一手动/定时发布事件，落地事务 outbox、任务租约、退避和失败可见性。

阶段出口：代理部署、重启、重复请求和外部服务失败测试全部通过；发布后的外部副作用具备可追踪状态。

### 阶段二：内容与扩展契约闭合

- 打通封面从媒体引用到公开渲染的全链路。
- 完成主题设置、样例渲染、校验和复核、原子激活和安全回退。
- 收紧插件路由、设置和事件/任务版本契约。

阶段出口：发布、回滚、导入导出和主题切换均有自动化验证，坏主题或坏插件不能破坏当前站点。

### 阶段三：规模和运维能力

- 将内容、页面、媒体、taxonomy 和搜索路径改为轻量投影、批量查询和有界分页。
- 增加页面缓存请求合并和后台任务可观测性。
- 增加备份加密选项、异地存储适配、验证/恢复演练和 Web 运维摘要。

阶段出口：在固定数据集和资源预算下，性能门禁、恢复演练和长时间任务运行均有可重复结果。

### 阶段四：产品体验和公共能力

- 修订 diff/恢复预览、批量内容操作、排程日历和 Owner/站点设置。
- 完善评论管理、双重确认订阅和签名退订。
- 增强 API 游标/过滤/增量同步、ETag、SEO 社交图和 Feed。

阶段出口：高频维护任务减少重复操作；API、SEO 和订阅行为有明确文档与兼容策略。

## 7. 统一验收标准

### 安全

- 在 Caddy 后，不同客户端不会因共享代理地址被错误合并；不可信转发头不能伪造来源。
- 所有新增或修改的公开写入接口均覆盖授权/CSRF、幂等或重放处理、速率限制、错误响应和审计要求。
- Webhook、退订 token、备份和日志均不泄露密码、会话、密钥、完整邮箱或访客隐私数据。
- 外部网络请求有超时、重定向策略、私网地址拒绝和失败重试语义。

### 数据与可靠性

- 手动发布、定时发布和回滚对外产生一致、版本化、幂等的事件语义。
- 进程在事务提交后立即退出时，outbox 任务仍能在下次启动继续执行。
- 失败任务不会无限增长或无限重试；管理员能看到原因、下一次尝试时间并安全重试。
- 封面、重定向、媒体引用和修订在发布、回滚、归档、导入导出后保持一致。

### 性能与运维

- 列表查询不带正文，分页和上传/导入/媒体处理均有明确上限。
- 测试数据达到约 1 万条内容、存在大正文和较多媒体变体时，内存和数据库连接仍受预算约束。
- 备份可验证、可恢复，恢复演练不覆盖现有数据；恢复后健康检查和公开页面可用。

### UI 与可访问性

- 关键流程保留无 JavaScript 路径，键盘焦点、可见焦点环、ARIA 状态和窄屏布局不回归。

## 9. 明确不建议纳入近期范围

在没有新的产品决策和 ADR 之前，建议继续排除以下方向：

- 多用户、角色/权限、读者账户、会员体系和多租户；
- 全量 SPA、全局客户端状态或新的前端框架；
- 为生产基线强行引入 Redis、独立消息队列或独立搜索服务；
- 在线插件市场、任意脚本执行、主题服务端代码执行；
- 支付、社交网络、复杂推荐和与博客核心闭环无关的增长功能。

这些方向会显著扩大安全面、运维面或产品边界，当前不如先把代理安全、事件可靠性、媒体闭环、主题契约和恢复能力做扎实。

## 10. 首批可直接拆分的任务

1. **客户端身份边界**：盘点所有 `RemoteAddr` 使用点，增加可信代理配置和统一解析测试。
2. **发布 outbox**：列出所有改变公开渲染的写路径，统一事件版本、事务记录和重启恢复测试。
3. **封面闭环**：从编辑器字段开始，贯通 publishing 查询、公开 view model、主题、媒体引用保护和导入导出。
4. **主题安装验收**：补充 manifest/schema、固定 fixture 渲染矩阵、校验和复核和原子回退测试。
5. **列表查询瘦身**：先移除 dashboard/公开列表的正文加载，再处理 taxonomy N+1 和媒体变体批量读取。
6. **运维摘要**：将失败任务、备份新鲜度、存储使用量和最近恢复结果统一呈现在管理台。
7. **Owner/站点设置**：补齐密码、TOTP、恢复码、会话和基础站点元数据的 Web 管理流程。

每个任务完成时都应同时更新对应设计文档、验收测试和运维说明，避免代码能力与文档契约再次分叉。
