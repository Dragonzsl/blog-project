# 阶段三：10,000 篇文章并发实测与瓶颈报告

> 实测日期：2026-09-05
>
> 数据集：10,000 篇已发布文章；单篇正文 5,824 bytes；每篇文章包含一个分类和一个标签。
>
> 测试入口：[phase3_http_load_test.go](../../internal/app/phase3_http_load_test.go)
>
> 后续方案：[阶段三性能深度优化方案](../development/phase-three-performance-optimization-plan.md)

## 1. 结论先行

当前默认配置下，必须区分缓存命中和冷缓存两种上限：

| 场景 | 实测结论 | 依据 |
| --- | --- | --- |
| 文章列表/详情缓存命中 | 测到 128 并发无 HTTP 错误，但在 16 并发开始不稳定地超过 ADR-0031 的 25 ms p95 门槛；128 并发 p95 为 91–181 ms | 同一缓存 key 的 256 次请求，数据库读等待开始增长 |
| 不同文章冷缓存 | 32 并发、128 请求全部 200，但 p95 已达 18.87 s；64 并发出现 47 个 500，128 并发出现 72 个 500 | 默认读连接池为 2；读等待和 30 s 渲染截止时间同时饱和 |
| 首页/分类/标签 | 10,000 篇数据下单请求已经失败，不需要并发即可复现 | 分类和标签查询各自超过 10 s；首页最终在 30 s 后返回 500 |

因此：

- 如果“上限”按不返回错误计算，缓存命中请求至少通过了 128 并发；这不是系统硬上限，只表示本轮未以错误率触顶。
- 如果按 ADR-0031 的缓存 p95 ≤25 ms 计算，当前环境的保守可接受档位是 8 并发；16 并发已越过门槛。
- 对不同文章的冷缓存流量，当前无错误边界位于 32 和 64 并发之间；但 32 并发的 18.87 s p95 已远超首次渲染 ≤150 ms 的预算，所以不能视为可接受的生产容量。
- 第一优先级瓶颈不是网络，而是分类/标签 SQL；第二优先级是 SQLite 2 连接读池在冷渲染时排队；第三优先级是首次渲染、磁盘缓存写入和搜索索引成本。

## 2. 测试方法

测试在应用完整路由上使用 `httptest.NewServer` 发起真实 HTTP 请求，数据库使用临时 SQLite WAL 数据库。配置与默认部署一致：

- Writer 连接数：1；Reader 连接数：2。
- 页面缓存和主题使用应用默认实现。
- 文章列表/详情缓存命中场景每个并发档位 256 请求。
- 冷文章场景使用不同 permalink，避免缓存命中；补测使用 128 请求，覆盖 32、64、128 并发。
- 并发档位：1、2、4、8、16、32、64、128。
- 每个请求记录状态码、耗时、响应字节数、缓存状态、读写连接池等待、堆变化和 goroutine 数量。
- 测试进程直接运行在当前工作环境，未经过 Caddy、TLS、容器 CPU 限制或外部网络。

完整矩阵命令：

```bash
PHASE3_LOAD_REQUESTS=256 PHASE3_LOAD_COLD_REQUESTS=32 \
go test -tags 'fts5 sqlite_omit_load_extension phase3load' ./internal/app \
  -run TestPhase3HTTPConcurrency -count=1 -v
```

冷缓存上限补测命令：

```bash
PHASE3_LOAD_LEVELS=32,64,128 \
PHASE3_LOAD_SCENARIOS=cold-article \
PHASE3_LOAD_COLD_REQUESTS=128 \
PHASE3_LOAD_SKIP_PROBES=1 \
go test -tags 'fts5 sqlite_omit_load_extension phase3load' ./internal/app \
  -run TestPhase3HTTPConcurrency -count=1 -v
```

## 3. 实测结果

### 3.1 建库和搜索索引

同一测试 fixture 的 `SyncAllDirty` 同步 10,000 个搜索文档耗时约 37.2–40.3 s；完整矩阵的一次结果为 38.58 s。它是一次性构建成本，不是每次普通文章读取都会发生的成本，但导入或全量重建时会形成明显后台任务压力。

服务级查询探针结果：

| 查询 | 结果 |
| --- | ---: |
| 已发布文章卡片 | 4.1 ms |
| 单篇公开文章 | 13.3 ms |
| 公共分类摘要 | 10.0 s 超时 |
| 公共标签摘要 | 10.0 s 超时 |
| 导航 | 0.8 ms |
| 归档索引 | 108 ms |
| 中文搜索服务调用（已完成索引同步） | 2.43 s |

### 3.2 缓存命中 HTTP 请求

以下为完整矩阵中的 p95，所有档位均为 0 错误、0 非 200 响应：

| 并发 | `/articles` p95 | 单篇文章 p95 |
| ---: | ---: | ---: |
| 1 | 1.48 ms | 1.87 ms |
| 8 | 5.65 ms | 11.10 ms |
| 16 | 28.82 ms | 30.79 ms |
| 32 | 19.51 ms | 27.35 ms |
| 64 | 47.50 ms | 49.31 ms |
| 128 | 181.44 ms | 91.50 ms |

16 并发以后 p95 已不再稳定满足 25 ms 门槛；128 并发仍未出现错误，但延迟明显退化。缓存命中请求的读等待在 128 并发约为 4.46–4.47 s 的累计等待时间，说明请求仍会争用 2 个 reader 连接或相关页面数据读取。

### 3.3 不同文章冷缓存请求

冷缓存补测使用 128 个不同文章路径：

| 并发 | 请求数 | p50 | p95 | 状态码 | 读等待 |
| ---: | ---: | ---: | ---: | --- | ---: |
| 1 | 32 | 603 ms | 816 ms | 200:32 | 0 次 |
| 8 | 32 | 1.88 s | 2.54 s | 200:32 | 467 次 / 41.24 s |
| 32 | 128 | 9.96 s | 18.87 s | 200:128 | 1,906 次 / 21m24.7s |
| 64 | 128 | 22.06 s | 30.36 s | 200:81、500:47 | 1,923 次 / 44m37.2s |
| 128 | 128 | 32.57 s | 33.02 s | 200:56、500:72 | 1,949 次 / 54m20.5s |

读等待时间是所有请求等待时间的总和，不是单个请求耗时。Writer 等待在这些场景均为 0；瓶颈集中在读连接池、SQLite 读取和冷渲染链路。

### 3.4 首页单请求

首页在没有任何并发压力时：

```text
status=500 duration=30.06s
```

页面渲染使用 30 s 的独立截止时间。首页会调用公共分类摘要；分类 SQL 在 10 s 探针中未完成，最终使首页渲染超时并返回 500。

## 4. 瓶颈定位

### P0：分类/标签摘要查询随文章数急剧放大

`internal/organization/repository.go` 的 `PublicCategories` 对每个分类执行 3 个“最新文章”相关子查询；这些子查询反复连接 `contents` 和 `content_revisions`，过滤 `category_public_id` 后再排序取 1 条。`PublicTags` 还要对每篇修订执行 `json_each(tag_public_ids_json)`，并同样重复 3 个相关子查询。

当前模式没有为 `content_revisions.category_public_id` 提供对应的公开查询路径，标签关系又存储在 JSON 中，导致 10,000 篇数据时出现重复扫描和 JSON 展开。首页、分类页、标签页和搜索页都会触发其中一部分；搜索页在执行 FTS 查询前还会先加载分类和标签选项。

### P0：默认 2 个 reader 连接成为冷渲染排队点

数据库代码固定 Writer 为 1 个连接，Reader 按 `database.read_connections` 建立有限连接池；默认值为 2。冷文章请求各自读取文章、分类/标签、媒体和站点数据并进行 Markdown/模板渲染，无法通过同一缓存 key 合并。并发从 32 提升到 64 后，读等待继续累积，部分请求跨过 30 s 渲染截止时间并返回 500。

仅增加 reader 数量不能解决分类/标签 SQL，但可以作为隔离实验验证池大小影响；配置上限目前为 8，仍需要在目标容器 CPU/内存预算内重新压测。

### P1：首次渲染和缓存写入本身超过首次渲染预算

并发 1 的不同文章冷缓存 p95 已为 816 ms，远高于 ADR-0031 的 150 ms 首次渲染预算。冷路径包含数据库读取、公开视图组装、Markdown/模板渲染、响应输出和页面缓存落盘；`RenderFlight` 只能合并相同 key 的同时 miss，不会合并不同文章的请求。

### P1：中文搜索索引构建和查询成本较高

10,000 篇长正文全量索引约需 38 s；已完成索引后，中文搜索服务调用仍约 2.43 s，超过 ADR-0031 的 250 ms 搜索预算。实际 `/search` 路由还会先加载分类和标签选项，因此在当前数据集上会受到 P0 分类/标签瓶颈的额外影响。

## 5. 建议的改进顺序

本次只做测量，没有修改生产查询或放宽资源预算。建议后续按以下顺序处理：

1. 重写公共分类/标签摘要为一次聚合加批量最新文章读取；为分类关系增加可用索引，逐步把标签 JSON 关系迁移到可索引的关系表或等价投影。
2. 先解决分类/标签查询，再分别以 reader=2、4、8 重跑冷文章矩阵；不要用增大连接池掩盖单条 SQL 的扫描问题。
3. 分离首次渲染的 Markdown/模板耗时、缓存落盘耗时和数据库耗时，必要时增加受控的预热或异步缓存写入。
4. 优化中文搜索的 `search_grams` 计数/分组查询和索引重建批处理，并单独压测搜索 HTTP 路径。
5. 在具备 Docker 权限的环境按 0.85 CPU、256 MiB 容器和 192 MiB Go heap soft limit 重跑；当前宿主机结果不能直接承诺生产 RPS。

## 6. 测试边界

- 当前结果来自同一进程内的 Go HTTP server 和客户端，不包含 Caddy、TLS、真实网络和多实例竞争。
- 当前环境无法执行 Docker Compose 资源限制下的实测，也没有启用 CPU/heap profile；所以报告给出的是当前默认配置下的容量边界和瓶颈证据，不是生产部署的绝对 RPS 承诺。
- 测试使用临时数据库，测试数据和索引不会写入项目运行数据。
- 主题插件、默认主题回归文件和已有 `.playwright-results/` 运行产物未纳入本次测量改动。
